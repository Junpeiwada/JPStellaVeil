## 0. 再開時にやること（最短手順）

```bash
git clone https://github.com/Junpeiwada/JPStellaVeil.git
cd JPStellaVeil
xcodegen generate
xcodebuild test -project JPStellaVeil.xcodeproj -scheme JPStellaVeil -destination 'platform=macOS'
```

テスト 131 件が成功すれば、環境構築は完了である。次は「5. フェーズ5に向けて」から着手する。

### 環境の前提

| 項目 | 内容 | 未導入時の対応 |
| --- | --- | --- |
| XcodeGen | `*.xcodeproj` は追跡していないため必須 | `brew install xcodegen` |
| Metal Toolchain | `.metal` の事前コンパイルに必要（約 690MB） | `xcodebuild -downloadComponent MetalToolchain` |
| ExifTool | メタデータ検証に使用 | `brew install exiftool`（無い場合テストは XCTSkip、アプリは警告表示で動作） |
| GPU | Metal 3 対応 | 動作実績: AMD Radeon Pro 5500M / Apple M4 Pro |

`Sources/` を追加・削除したら **必ず `xcodegen generate` を実行する**。実行しないと新しいファイルがビルド対象に入らず、「テストを書いたのに実行されない」という状態になる（実際に一度踏んだ）。

### テストデータ

```
/Volumes/RAID1-8T4/Storage2025/2026/2026-08-12/A1_04276-Mean Max Hor Accuracy.tif
```

8640 x 5760 / 16-bit / 64-bpp（RGBA・Associated Alpha）/ ProPhoto RGB（ROMM RGB）。
天の川と、人工光を放つゲル群（前景）が同居する。**このファイルは書き換えないこと。**
このファイルが無い環境では、該当テストは `XCTSkip` する作りになっている。
**別マシンで Dropbox のパスが違う場合、テスト内のパス定数を修正する必要がある**（`TIFFColorManagementTests.swift` と `TIFFImageIOServiceTests.swift` に直書きされている）。

### 動作確認用の環境変数

アクセシビリティ権限が無い環境では UI 自動操作ができないため、起動時に状態を作る仕組みを用意している。

```bash
APP=~/Library/Developer/Xcode/DerivedData/JPStellaVeil-*/Build/Products/Debug/JPStellaVeil.app
JPSTELLAVEIL_OPEN_FILE="/path/to/test.tif" \
JPSTELLAVEIL_ADD_PRESET=standard \
JPSTELLAVEIL_AUTO_APPLY=1 \
JPSTELLAVEIL_DISPLAY_EXPOSURE=6.0 \
JPSTELLAVEIL_SPLIT=0.5 \
JPSTELLAVEIL_ZOOM=200 \
"$APP/Contents/MacOS/JPStellaVeil"
```

| 変数 | 意味 |
| --- | --- |
| `JPSTELLAVEIL_OPEN_FILE` | 起動時に開く TIFF |
| `JPSTELLAVEIL_ADD_PRESET` | 起動時に追加するレイヤー（`fine` / `standard` / `wideHalo`） |
| `JPSTELLAVEIL_AUTO_APPLY` | `1` で起動時にフル解像度処理まで実行する（現在は値の変更で自動処理されるため通常は不要） |
| `JPSTELLAVEIL_DISPLAY_EXPOSURE` | 表示専用の露出倍率。星空は暗いので 6 程度にすると見える |
| `JPSTELLAVEIL_SPLIT` | スプリット比較の境界（0 で全面処理結果、1 で全面原画） |
| `JPSTELLAVEIL_ZOOM` | 表示倍率（`100` で等倍）。グローの形は縮小表示では潰れる |
| `JPSTELLAVEIL_GLOW_ONLY` | `1` でグローのみ表示にする。グロー成分は暗いので露出は 20 程度が見やすい |

`open -n` では環境変数が引き継がれないため、実行バイナリを直接起動すること。

### スクリーンショットの撮り方

バイナリ直接起動ではウィンドウが前面に来ないため、全画面キャプチャでは写らない。
ウィンドウ ID を取得して、そのウィンドウだけを撮る。

```swift
// findwindow.swift
import CoreGraphics
import Foundation

let list = CGWindowListCopyWindowInfo([.optionOnScreenOnly, .excludeDesktopElements], kCGNullWindowID) as? [[String: Any]] ?? []
for window in list {
    guard let owner = window[kCGWindowOwnerName as String] as? String,
          owner.contains("JPStellaVeil"),
          let number = window[kCGWindowNumber as String] as? Int else { continue }
    print(number)
}
```

```bash
WID=$(swift findwindow.swift | head -1)
screencapture -x -o -l "$WID" shot.png
```

## 2. 実装済み機能の要点（ハマりどころ）

### 2.1 ICC プロファイル比較には落とし穴がある

同じ色空間でも **取得経路によって名前の文字列が違う**。

| 経路 | 返る値 |
| --- | --- |
| `CGColorSpace.name` | `kCGColorSpaceLinearSRGB`（システム識別子） |
| ImageIO の `kCGImagePropertyProfileName` | `sRGB IEC61966-2.1 Linear`（ICC 記述名） |

このため `ColorProfileInspector` は **ICC プロファイルの `desc` タグを直接パース**して名前を得る。
ICC v2 は `desc`（textDescriptionType）、v4 は `mluc`（multiLocalizedUnicodeType）で、
**`mluc` のレコード内オフセットはタグデータ先頭からの相対**（プロファイル先頭ではない）。ここを間違えるとヘッダの断片が文字列として返る。

### 2.2 書き出し時にプロファイル名を持ち込んではいけない

`writeTIFF` に入力のプロパティ辞書を渡すと入力の `ProfileName` が混入し、
実際に埋め込まれる `CGImage.colorSpace` と食い違って ICC 検証が誤判定する。
そのため `kCGImagePropertyProfileName` を明示的に削除している。出力の ICC は `image.colorSpace` が決める。

### 2.3 色管理の 2 系統

- **中間 TIFF**: `linearSRGB` を埋め込む。入力プロファイルと一致しないのが正常。
- **最終 TIFF**: 処理後に入力 ICC へ戻して埋め込む。

検証は `ExpectedOutputProfile`（`.workingSpace(.linearSRGB)` / `.matchesInput`）で期待値を明示する。

### 2.4 ExifTool の `SourceFile` は除外必須

`-j` 出力にはグループ修飾なしの `SourceFile`（ファイルパス）が含まれ、入出力で必ず異なる。
除外しないと必ず検証失敗になる。除外タグの全リストは [技術仕様 §3.2](../技術仕様.md#32-比較から除外する対象) にある。

### 2.5 スプリット比較の既定値は 0.0（フェーズ4で修正）

シェーダは `texCoord.x > splitPosition` のとき処理結果を描く。
つまり **0.0 が全面処理結果**で、1.0 は全面原画である。
フェーズ3までは既定値が 1.0 で「全面が処理結果」とコメントされていたが、実装とは逆だった。
処理結果テクスチャが常に nil だったため表示が変わらず、フェーズ4で処理結果が入って初めて表面化した。

### 2.6 `read_write` テクスチャは避けている

Metal の `access::read_write` は read-write tier 2 を要求する。
tier 1 の GPU では `rgba16Float` が使えないため、累積と合成は
読み込み用と書き込み用を分ける ping-pong 構成にしてある。バッファが 2 枚 1 組なのはこのため。

### 2.7 タイルのマージンは 2 つのぼかし半径の和

背景減算のぼかしとグローのぼかしは直列に掛かる。
マージンを「グロー半径だけ」にすると、タイル端の背景推定が不正確になり、
その誤差がグローに乗って格子状の継ぎ目として見える。
`GlowPipelineTests.testTiledResultMatchesSingleTileResult` が、
タイル分割の結果と単一タイル処理の結果が一致することを検証している。

### 2.8 テストデータはリニアではなかった

当初「星空写真はリニアのままでは真っ黒」と想定したが、実際は表示露出 x1.0 で正常に見えた。
このファイルは既にガンマ適用済みで、それを linearSRGB として取り込み表示時に再度 sRGB エンコードしているため、結果的に元の見え方になっている。
表示露出スライダーは暗い素材のために残してある（**表示専用。書き出しには影響しない**）。

## 3. キャンバス描画の構造

`CanvasRenderer` が 3 枚のテクスチャをフラグメントシェーダで合成する。

| インデックス | テクスチャ | 未設定時 |
| --- | --- | --- |
| 0 | 処理結果 | 原画で代替 |
| 1 | 原画 | 必須 |
| 2 | マスク（R 成分） | 原画で代替、`hasMask=0` |

- 拡大縮小と位置は **テクスチャ座標で表現**する。ビューポートは描画領域全体に固定。
  当初はビューポートで表現していたが、等倍以上でビューポート幅が Metal の上限（16384）を
  超えて描画が破綻していた（8640px の画像を等倍表示すると Retina で 17280px になる）。
  パンすると歪み方が変わるため「2 本指ドラッグでアスペクト比が変わる」症状として現れた。
- パン可動域は `CanvasViewState.clampedPanOffset` で丸める。画像がビューより小さい軸は可動域 0。
- Fit 表示ではパンを無視して中央固定。

操作の割り当て:

| 操作 | 挙動 |
| --- | --- |
| ドラッグ | パン |
| Command+スクロール / ピンチ | ズーム |
| スペースキー押下中 | 元画像比較 |
| Option+ドラッグ | スプリット比較の境界移動（境界より右が処理結果） |

元画像比較は当初マウス押下に割り当てていたが、`mouseDown` で必ず比較に入るため
**ドラッグしてもパンできない**状態だった。フェーズ4完了後にスペースキーへ移した。
スペースキーを受け取るため、キャンバスは表示時とクリック時にファーストレスポンダになる。

## 4. フェーズ4の実装結果（決定事項はフェーズ5以降も守ること）

**4.1〜4.3 はユーザーとの合意事項である。以降のフェーズでも守ること。**

### 4.1 プレビューを縮小してはならない

初期案では「プレビューは長辺 2048px に縮小」としたが、**ユーザーから明確に否定された**。

> いや縮小してはいけません 見た目がかわってしまうから 処理が遅くても仕方ないです

- **常にフル解像度（8640x4860）で処理する。**
- 縮小による見た目の差を作らない。プレビューと書き出しの結果を完全に一致させる。
- 処理が遅いことは許容する。

### 4.2 自動処理（当初は適用ボタン方式だった）

当初の合意は「適用ボタンを押したときだけ処理する」だった。

> 適用ボタンを作って　スライダーにリアルタイムで反応しなくてよい。

**フェーズ4完了後に自動処理へ変更した。** フル解像度でも 0.2 秒程度と十分速かったため。

> 結構速いので、適用ボタン押さずスライダーの変化で即時描画で大丈夫かも

- パラメータ変更、レイヤーの表示切替、表示モード変更で自動的に処理が走る。
- 150ms のデバウンスを挟む（スライダーのドラッグ中に処理を投げ続けないため）。
- 実行中に新しい要求が来たら、古い処理はキャンセルして最新の値で処理し直す。
- 「中止」を押したときだけ自動処理が止まり、「適用」ボタンで再開する。

### 4.3 キャンセル可能・UI をブロックしない

> 処理中で簡単にキャンセルできるようなつくりにしましょう 他の操作をなるべくブロックしない形でつくりたい

- **タイル分割**して処理する。`MTLCommandBuffer` は投入したら止められないため、
  1 タイルごとにキャンセルフラグを確認する構造にする。
- 処理は専用のバックグラウンドキューで実行し、`@MainActor` は結果受け取りのみ。
- **段階表示**: 焼き上がったタイルから順にキャンバスへ反映する。全部終わるまで待たせない。
- 進捗（％またはタイル数）をステータスバーに出す。

### 4.4 実装した処理内容

タイルごとに、以下を 1 つのコマンドバッファへ詰めて投入する。

1. 合成先を元画像で初期化
2. 各レイヤーについて
   1. 背景推定（σ = 背景除去 px / 3、横 → 縦）
   2. 星抽出 `star = max(元画像 - 背景 - 明るさ下限, 0)`
   3. 4 成分 PSF（σ 倍率 0.25 / 0.60 / 1.00 / 2.20、重み 0.55 / 0.25 / 0.13 / 0.07）を
      横 → 縦で畳み込み、重み付きで累積
   4. `ゲイン = 強度 x 不透明度` を掛けて Screen または Add で合成
3. マージンを捨て、中央部だけを出力テクスチャへ書き戻す

グロー成分の畳み込みでは、**横パスの読み込み時に成分ごとの明るさしきい値を引く**。
広い成分ほど高いしきい値なので、暗い星は芯だけ、明るい星は裾まで乗る。
これが「明るい星ほど大きなハロー」の実体である（4.7 節）。

**各レイヤーは常に元画像から星を抽出する。** 合成先だけが積み上がる。
下のレイヤーの結果から星を抽出し直すわけではない。

不透明度をゲインへ畳み込めるのは、Screen も Add も
`mix(base, blend(base, glow), opacity) == blend(base, glow * opacity)` が成り立つため
（`BlendMath` のテストで検証している）。

### 4.5 タイル分割の設計

- マージン = 背景ぼかし半径 + 最大グロー半径（直列に掛かるので足す）
- タイル寸法 = マージン x 4 を 256 画素単位へ丸め、1024〜2048 に収める
- 実効半径は 3σ

中間バッファは `rgba16Float`（背景減算で負値、グロー加算で 1 超えが出るため）。
出力のみ `rgba16Unorm` で、CPU から読み戻せるよう
ユニファイドメモリなら `.shared`、ディスクリート GPU なら `.managed` にしている。

### 4.6 実測（Apple M4 Pro / 8640 x 4860 / 1 レイヤー）

| 設定 | 結果 |
| --- | --- |
| 標準グロー（半径 20px） | 45 タイル / 約 0.2 秒 |
| 広いハロー（半径 60px） | 約 0.6 秒 |

速すぎて進捗表示が一瞬で終わる。半径を大きくすると進捗とキャンセルが確認しやすい。

---

### 4.7 明るさ応答が要る理由

畳み込みは線形なので、しきい値が無いと星の明るさが変わっても PSF の**形**は変わらない。
振幅が比例するだけである。ガウシアンの裾は `exp(-r²/2σ²)` なので、
視認できる半径は `r ∝ √(ln B)` でしか増えない。
**明るさが 10 倍でもハロー半径は 1.5 倍程度**にしかならず、
実写で期待する「明るい星ほど大きなハロー」にならない。

そこで成分ごとに明るさしきい値を設け、PSF の形自体を明るさで変えている。

- 成分 i の入力は `smoothstep(t, t * 1.5, star) * star`（t = 明るさ応答 x しきい値係数_i）
  - 引き算にすると振幅まで落ちて明るい星の裾が痩せるため、ゲートとして掛ける
- しきい値係数は 0.00 / 0.05 / 0.15 / 0.35（芯 → 裾）
- 「明るさ応答」（0〜1、既定 0.5）で一括調整する。0 なら従来の線形挙動に戻る

追加のパスは要らない（横パスの読み込み時に引くだけ）ので、処理時間は変わらない。

### 4.8 グローのみ表示

`GlowOutputMode.glowOnly`。合成先を原画ではなく黒で初期化し、
すべてのレイヤーを加算合成するだけで実現している。専用のテクスチャは持たない。

- Screen 指定のレイヤーもこのモードでは加算になる（成分そのものを見るのが目的）。
- レイヤー別グローを保持しているので、切り替えても再処理は要らない（4.9 節）。

### 4.9 レイヤー別グローを保持している

グローは「畳み込み → ゲイン → 合成」の順に処理される。**後段はすべて線形**なので、
畳み込み結果を保持しておけば描画時に適用できる。

- 各レイヤーのグローを **ゲイン適用前**の `rgba16Float` フル解像度テクスチャで保持する
- 表示はキャンバスのフラグメントシェーダが毎フレーム合成する
- 書き出しは `compositeLayers` カーネルが同じ式で合成する

| 変更 | 扱い |
| --- | --- |
| 半径、背景除去、明るさ下限、明るさ応答 | 畳み込みからやり直す |
| 強度、不透明度、合成モード | 描画時に適用（再処理なし） |
| 表示/非表示、並べ替え、グローのみ表示 | 描画時に適用（再処理なし） |
| レイヤー追加 | 追加分だけ処理する（既存は再利用） |

判定は `GlowConvolutionKey`（半径・背景除去・明るさ下限・明るさ応答）で行う。
**非表示のレイヤーも畳み込んでおく**。表示切替を即座に反映するため。
同時に扱えるレイヤーは 8 枚（シェーダのテクスチャ配列サイズ）。

VRAM は 8640 x 4860 で 1 枚 336MB。原画 + グロー（レイヤー数分）+ 処理中の中間 149MB。
表示そのもの（ドロウアブル）は画面解像度の 8bit で 44MB 程度しかない。
**容量を使うのは表示ではなく画像データ本体**である。

## 5. 空マスク（実装済み）

Photoshop の「空を選択」を osascript 経由で借りる。実装は
[SkyMaskService.swift](../../Sources/Masking/SkyMaskService.swift) と、同梱する
[sky_mask.jsx](../../Scripts/sky_mask.jsx)。入力ファイルは開くだけで保存しない
（スクリプト側で `DONOTSAVECHANGES` で閉じる）。

フル解像度 8640x5760 で約 3 秒（Photoshop 起動済みの場合）、出力 3.8MB。

### 5.1 マスクの掛かり方

グローは畳み込んだあとにマスクを掛けるだけなので、畳み込み自体はマスクを知らない。
表示側（`CanvasShaders.metal`）と書き出し側（`GlowShaders.metal`）の**合成の段階**で適用する。
この作りのおかげでマスクの ON/OFF は再処理なしで切り替わる。

マスクは**プロジェクト共通の 1 枚**である。

### 5.2 自前生成と手動補正は実装しない（2026-08-25 決定）

地平線指定・境界ぼかし・手動ブラシ・レイヤーごとのマスクは取りやめた。
Photoshop の精度で用が足りており、直すときも Photoshop 側のほうが早い。
星景写真の空と地上の境界（木立・稜線・電線）はヒューリスティックが最も苦手とする形状で、
同等をアプリ単体でやるならセグメンテーションモデルの搭載が必要になる。

`SkyMaskState` の `horizonY` / `featherRadius` はドメインモデルに残っているが、
UI からも処理からも切り離されている（P5-10 で UI から削除済み）。

### 5.3 なぜマスクが要るかは実データで確認済み

指定テストデータで標準グローを適用したときの平均輝度増分は次のとおり。

| 領域 | 平均増分 |
| --- | --- |
| 空（上半分） | 0.00054 |
| 前景（下 1/4、ゲル群の照明） | 0.00165 |

**前景の人工光の方が 3 倍強く反応している。** これがマスクで抑えたい現象そのものである。
`GlowRealImageTests.testGlowRespondsMoreToPointsThanToFlatBrightAreas` がこの値を出力する。

## 6. 既知の課題

### 6.1 グロー全体の強さは未調整

明るさ応答（4.7 節）を入れたことで「明るい星ほど大きなハロー」にはなった。
ただしエネルギー保存の PSF（重み合計 1.0）である以上、点像を広げるとピークは下がる。
実写では標準グローで最大増分 0.276、明るくなった画素 34% と数値上は効いているが、
等倍表示での見た目は控えめである。
強度スライダーの上限（現在 5.0）やゲインの掛け方は、実写を見ながら調整する余地がある。
**ユーザーの判断を仰ぐこと。**

### 6.2 （解決済み）スプリット比較の境界が拡大表示でずれる

シェーダがテクスチャ座標で境界を判定していたため、拡大するとマウス位置とずれていた。
描画をテクスチャ座標方式へ変えた際に、境界判定も画面座標基準へ直したので解消済み。

### 6.3 テストデータのパスが直書き

`TIFFColorManagementTests.swift`、`TIFFImageIOServiceTests.swift`、`GlowRealImageTests.swift`
にフルパスが直書きされている。別マシンでパスが異なる場合は環境変数から読む形へ変えるとよい。

### 6.4 フェーズ7（進行中）の残作業

書き出し経路へのメタデータコピーと検証の接続（P7-2）、失敗時の中止と表示（P7-3）は完了済み。
実装は [AppState.swift](../../Sources/App/AppState.swift) の `exportFinalTIFF` と
[SidePanel.swift](../../Sources/App/SidePanel.swift) の「メタデータ検証」節。

残りは次のとおり。

- **P7-1**: ExifTool の同梱と署名・公証（現状はシステムインストール版を PATH から探索して使用）
- **P7-4**: 読み込み → 調整 → 書き出し → 検証の結合テスト
  （現在の `GlowExportIntegrationTests` は TIFF 往復までで、メタデータ検証まで通していない）
