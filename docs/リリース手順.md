GitHub Release で配布用の DMG を公開するまでの手順。

`v1.0.0` のようなタグを push すると、GitHub Actions が
ビルド → Developer ID 署名 → 公証 → DMG 作成 → 公証 → Release 作成
までを自動で行う。

---

## 署名資材の置き場

証明書と API キーは他のアプリと同じ流儀で Dropbox に置いてある。

```
~/Dropbox/アプリ/JPStellaVeil/
├── 証明書.p12                                          # Developer ID Application（秘密鍵つき）
├── パスワード.txt                                       # 上の .p12 のパスワード
├── Developer ID Application: Junpei Wada (...).cer     # 証明書単体（参考用）
├── AuthKey_5NFM2RND38.p8                               # 公証用の App Store Connect API キー
├── キーID.txt                                           # 5NFM2RND38
├── IssuerID.txt                                         # App Store Connect の Issuer ID（69a6de77-… で始まる UUID）
└── アプリ用パスワード.txt                                # 予備（API キー方式では使わない）
```

**Developer ID Application 証明書は Apple Developer アカウントに 1 枚あればよく、
全アプリで共有する。** JPScreenShot・JPPhotoTools と同一のものを使っている。
アプリごとに発行するものではない。

現在の証明書の有効期限は **2027 年 2 月 1 日**。切れる前に更新すること。

## 1. 初回だけ必要な準備

資材は上記のとおり揃っているので、GitHub Secrets へ登録するだけでよい。

```bash
Tools/Release/setup_github_secrets.sh
```

Dropbox のフォルダから読んで、次の 5 つを登録する。入力を求められる項目はない。
Secret 名は JPScreenShot / JPPhotoTools と同じ流儀に揃えてある。

| Secret 名 | 内容 |
| --- | --- |
| `DEVELOPER_ID_CERT_P12` | `証明書.p12` を base64 化したもの |
| `DEVELOPER_ID_CERT_PASSWORD` | `パスワード.txt` の中身 |
| `ASC_API_KEY_P8` | `AuthKey_*.p8` を base64 化したもの |
| `ASC_KEY_ID` | `キーID.txt` の中身 |
| `ASC_ISSUER_ID` | `IssuerID.txt` の中身 |

自動更新（Sparkle）用に、もう 1 つ手動で登録済みのものがある。

| Secret 名 | 内容 |
| --- | --- |
| `SPARKLE_PRIVATE_KEY` | appcast 署名用の EdDSA 秘密鍵（キーチェーンから `generate_keys -x` で書き出したもの） |

Team ID は秘密ではなく [project.yml](../project.yml) と
[ExportOptions.plist](../Tools/Release/ExportOptions.plist) に書いてあるので、Secret にはしない。

置き場を変えたい場合は環境変数で指定できる。

```bash
JPSTELLAVEIL_SECRETS_DIR=/path/to/dir Tools/Release/setup_github_secrets.sh
```

## 2. リリースする

[Tools/release.sh](../Tools/release.sh) が、バージョン更新からタグ push までを 1 コマンドで行う。

```bash
npm run release -- 1.2.0      # バージョンを渡して発火
npm run release               # 引数なし。現在の版を表示して対話入力
Tools/release.sh 1.2.0 -y     # 確認プロンプトを省略
Tools/release.sh --help       # 詳細
```

VSCode の NPM SCRIPTS パネルからクリックでも実行できる（[package.json](../package.json)）。
引数を渡せないので、現在の版を表示したうえでパッチを 1 つ上げた値を既定値として尋ねる。

スクリプトがやること:

1. `project.yml` の `MARKETING_VERSION` を更新
2. `xcodegen generate` で yml の妥当性を早期検証
3. `project.yml` をコミット
4. タグ `v<version>` を打って main とタグを push → Actions が発火

ワーキングツリーが汚れている、タグが既に存在する場合は中断する。
指定番号が現在と同じか古い場合は警告する。

進行状況は Actions タブ、または `gh run watch` で見られる。
公証を 2 回通すため、完了まで 10〜20 分ほどかかる。

タグを打たずに実行したい場合は、Actions タブから Release ワークフローを
手動実行し、バージョン番号を入力する。

## 3. 手元で確認する

CI と同じ手順を手元でも再現できる。実際にこの手順で公証まで通してある。

```bash
SECRETS_DIR=~/Dropbox/アプリ/JPStellaVeil
KEY_PATH="$(find "$SECRETS_DIR" -maxdepth 1 -name 'AuthKey_*.p8' | head -1)"
KEY_ID="$(tr -d '\r\n' < "$SECRETS_DIR/キーID.txt")"
ISSUER_ID="$(tr -d '\r\n' < "$SECRETS_DIR/IssuerID.txt")"

xcodegen generate

xcodebuild archive \
  -project JPStellaVeil.xcodeproj \
  -scheme JPStellaVeil \
  -configuration Release \
  -destination 'generic/platform=macOS' \
  -archivePath /tmp/JPStellaVeil.xcarchive \
  CODE_SIGN_STYLE=Manual \
  CODE_SIGN_IDENTITY="Developer ID Application"

xcodebuild -exportArchive \
  -archivePath /tmp/JPStellaVeil.xcarchive \
  -exportOptionsPlist Tools/Release/ExportOptions.plist \
  -exportPath /tmp/export

# アプリ本体を先に公証してチケットを埋める
Tools/Release/notarize.sh /tmp/export/JPStellaVeil.app "$KEY_PATH" "$KEY_ID" "$ISSUER_ID"

Tools/Release/make_dmg.sh /tmp/export/JPStellaVeil.app /tmp/JPStellaVeil.dmg
codesign --force --sign "Developer ID Application" --timestamp /tmp/JPStellaVeil.dmg

# DMG も公証する
Tools/Release/notarize.sh /tmp/JPStellaVeil.dmg "$KEY_PATH" "$KEY_ID" "$ISSUER_ID"
```

最後に、ダウンロードしたユーザーと同じ判定を再現して確かめる。

```bash
spctl -a -t open --context context:primary-signature -vv /tmp/JPStellaVeil.dmg
```

`source=Notarized Developer ID` と出れば、警告なしに起動できる状態になっている。

## 補足

### なぜ公証を 2 回通すのか

DMG だけを公証すると、DMG にはチケットが埋まるがアプリ本体には埋まらない。
その状態でアプリを Applications へコピーし、オフライン環境で初めて起動すると、
Gatekeeper がチケットを取得できず弾かれることがある。

アプリ本体を先に公証・staple してから DMG に詰め、DMG も公証することで、
どちらの経路でもオフラインで検証が完結する。

### 自動更新（Sparkle）

インストール済みのアプリは、起動時に GitHub Pages 上の appcast を見て更新を確認する。

| 項目 | 値 |
| --- | --- |
| フレームワーク | Sparkle 2.9.6（SPM 依存） |
| 更新フィード | `https://junpeiwada.github.io/JPStellaVeil/appcast.xml` |
| 確認間隔 | 24 時間（起動時 ON。メニューから切替可能） |
| 更新に使う配布物 | Release に添付した zip（DMG は人が手で入れる用） |

リリースのたびに CI が `generate_appcast` で appcast.xml を作り直し、gh-pages ブランチへ publish する。
appcast は EdDSA 署名され、アプリ側は Info.plist の `SUPublicEDKey` で検証する。

**署名鍵は JPPhotoTools と共有している。** `generate_keys` はキーチェーンに保存済みの鍵を
再利用するため、同じマシンで作った他アプリと同一の鍵になる。公開鍵
`WiyUPbS5LnynuM2+J8Z/n+nRIhbjDpwtD/rbmcWeGVg=` が両アプリの Info.plist に入っている。

Sparkle の任意キー（`SUFeedURL` / `SUPublicEDKey`）は `INFOPLIST_KEY_*` では注入できないため、
Info.plist は自動生成をやめて [project.yml](../project.yml) の `info` ブロックから実ファイルを生成している。
設定を変えるときは project.yml を編集して `xcodegen generate` すること。

### 署名だけでは足りない理由

Hardened Runtime を有効にしたうえで公証を通し、結果を staple すると、
ダウンロードしたユーザーは警告なしにアプリを開ける。
署名だけで公証が無いと、初回起動時に「開発元を確認できません」と表示され、
右クリックからの起動が必要になる。

### Photoshop の操作許可について

[SkyMaskService.swift](../Sources/Masking/SkyMaskService.swift) は `osascript` 経由で
Photoshop を操作する。Hardened Runtime 下でこれを許可するため、
`com.apple.security.automation.apple-events` を entitlements に入れてある。
署名済みアプリの初回実行時、システムが Photoshop の操作許可を尋ねる。
誤って拒否した場合は、システム設定 →「プライバシーとセキュリティ」→「オートメーション」
から許可し直せる。

### テストターゲットの Team ID について

[project.yml](../project.yml) の `DEVELOPMENT_TEAM` は全ターゲット共通に設定してある。
テストバンドルはホストアプリへ読み込まれるため、Hardened Runtime 下では
Team ID が一致していないと `different Team IDs` で拒否され、テストが起動しない。

### ExifTool は同梱していない

配布物に ExifTool は含めていないため、利用者側で `brew install exiftool` が必要になる。
未導入の場合はメタデータの補完と検証が行われず、その旨がサイドパネルと
ステータスバーに表示される。
