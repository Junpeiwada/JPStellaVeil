## 1. アーキテクチャ

| 層 | 使用技術 | 担当範囲 |
| --- | --- | --- |
| UI 層 | SwiftUI | レイヤーパネル、インスペクタ、ステータス表示 |
| 描画層 | MetalKit | キャンバス、ズーム、比較表示、マスクオーバーレイ |
| 演算層 | Metal Compute | 星抽出、PSF 畳み込み、合成、マスク適用 |
| IO 層 | ImageIO / ColorSync | 16bit TIFF 入出力、ICC 維持 |
| メタデータ層 | ExifTool（同梱予定） | メタデータのコピーと JSON 比較検証 |
| 永続化層 | Codable JSON | `.stellaveil` プロジェクトファイル |

実装上の重要原則:

- 抽出・ぼかし・合成は必ずリニア RGB で実行する。
- プレビューと最終出力の処理契約を一致させる（同一テクスチャを使う。§4.1 参照）。

## 2. 色管理仕様

フェーズ1で確定。

### 2.1 ICC の扱い

- 処理はリニア RGB（`linearSRGB`）で行う。
- 中間 TIFF: `linearSRGB` を埋め込む。入力プロファイルとは一致しないのが正常。
- 最終 TIFF: 処理後に入力 TIFF の ICC プロファイルへ変換して埋め込む。
- 検証は期待値を明示して行う（`ExpectedOutputProfile`）。
  - `.workingSpace(.linearSRGB)`: 中間出力に使用
  - `.matchesInput`: 最終出力に使用

### 2.2 ICC 一致判定の比較キー

- 比較キーはプロファイル記述名の正規化文字列。
- プロファイル名は ICC プロファイルの `desc` タグから取得する。
  - ICC v2 は `desc`（textDescriptionType）、v4 は `mluc`（multiLocalizedUnicodeType）に対応。
  - `CGColorSpace.name` はシステム識別子（`kCGColorSpaceLinearSRGB`）を返し、
    ImageIO の `kCGImagePropertyProfileName` は記述名（`sRGB IEC61966-2.1 Linear`）を返すため、
    両者を突き合わせるには `desc` タグ経由に統一する必要がある。
- 正規化規則: Unicode 互換正規化 → 小文字化 → 英数字以外を除去。
  - 例: `Adobe RGB (1998)` と `adobe-rgb-1998` は同値。
- どちらかがプロファイル名不明の場合は不一致として扱う（保存を止める側に倒す）。
- TIFF の `Model` タグ（カメラ機種名）をプロファイル名の代用にはしない。

## 3. メタデータ比較仕様

フェーズ1で確定。

### 3.1 ExifTool 呼び出し

- 読み取り: `-G:0 -j -a -u -n`（グループ修飾付き、JSON、重複/未知タグ含む、数値変換なし）
- コピー: `-TagsFromFile <入力> -all:all -overwrite_original <出力>`
- 実行ファイル探索順: 明示指定 → アプリバンドル同梱 → `/opt/homebrew/bin` → `/usr/local/bin` → `/usr/bin` → PATH

### 3.2 比較から除外する対象

- グループ: `ExifTool`、`File`、`Composite`
- タグ名接頭辞: `ExifTool`、`Warning`、`Error`
- ファイル実体依存: `SourceFile`、`FileName`、`Directory`、`FileSize`、`FileModifyDate`、
  `FileAccessDate`、`FileInodeChangeDate`、`FilePermissions`、`FileTypeExtension`
- TIFF 物理レイアウト（再エンコードで必ず変わる）: `StripOffsets`、`StripByteCounts`、
  `RowsPerStrip`、`TileOffsets`、`TileByteCounts`、`TileWidth`、`TileLength`、
  `Compression`、`PlanarConfiguration`、`Predictor`、`PhotometricInterpretation`、`FillOrder`
- 書き出しツール名: `Software`、`ProcessingSoftware`
- サムネイル再構築: `ThumbnailOffset`、`ThumbnailLength`、`ThumbnailImage`、`PreviewImage`
- ICC（色管理検証で別途扱うため二重に見ない）: `ProfileCMMType`、`ProfileDateTime`、
  `ProfileID`、`ProfileCreator`

### 3.3 値の正規化規則

1. Unicode 互換正規化
2. 連続空白（改行・タブ含む）を単一スペースへ畳み、前後を除去
3. 先頭の日付区切りを `YYYY:MM:DD` 表記へ統一（`2026-08-24` → `2026:08:24`）
4. 有理数表記を小数へ評価（`3/1` → `3`、分母 0 はそのまま）
5. 数値として解釈できる場合は表記統一（`1.50` → `1.5`、有効桁 6 桁）

### 3.4 判定

- 差分種別: 出力欠落 / 出力側余剰 / 値不一致
- 差分が 0 件のときのみ検証成功。
- 検証失敗時は出力ファイルを削除し、失敗タグを表示する。

## 4. 処理パイプライン

フェーズ4で確定。

### 4.1 プレビューは縮小しない

- プレビューも書き出しも **常にフル解像度**（指定テストデータでは 8640 x 4860）で処理する。
- 縮小処理を挟むと見た目が変わるため採用しない。処理時間が長くなることは許容する。
- 結果としてプレビューと最終出力の見え方は原理的に一致する。

### 4.2 自動処理（当初は適用ボタン方式）

**当初は「適用ボタンを押したときだけ処理する」方式だったが、フェーズ4完了後に自動処理へ変更した。**
フル解像度でも標準設定なら 0.2 秒程度と十分速いことが実測で分かったため。

- パラメータ変更、レイヤーの表示切替、表示モード変更で自動的に処理を開始する。
- スライダーのドラッグ中に処理を投げ続けないよう 150ms のデバウンスを挟む
  （`AppState.autoApplyDelay`）。
- 実行中に新しい要求が来たら、古い処理をキャンセルして最新の値で処理し直す。
- ユーザーが「中止」を押したときだけ自動処理を止める（`isAutoApplyEnabled`）。
  再開は「適用」ボタン。勝手に再開すると中止した意味がなくなるため。
- `AppState.previewUpdateGeneration` と「最後に適用した generation」の比較で未適用状態を判定する。

### 4.3 キャンセル可能・非ブロッキング

- 処理はタイル分割して行い、タイル投入前にキャンセルフラグを確認する。
  `MTLCommandBuffer` は投入後に停止できないため、キャンセル粒度はタイル単位とする。
- 処理は専用のバックグラウンドキューで実行し、メインスレッドは結果受け取りのみ行う。
- 焼き上がったタイルから順にキャンバスへ反映し、完了まで待たせない。
- 進捗をステータスバーに表示する。

### 4.4 数値計算上の要件

- 中間バッファは `rgba16Float` を使う。16bit 整数では背景減算で負値が飛び、
  グロー加算で飽和するため。最終的に `rgba16Unorm` へ戻す。
- ガウシアンぼかしは分離可能フィルタ（横 → 縦の 2 パス）で実装する。
- 4 成分 PSF は半径の異なる 4 つのガウシアンの重み付き和とし、
  芯が明るく裾が長い天体写真特有の減衰形状を作る。
- タイル境界の継ぎ目を防ぐため、タイルに半径以上のマージンを持たせて処理し、
  中央部のみを書き戻す。

### 4.5 実装した処理内容

処理は次の順で行う。すべてリニア RGB、中間は `rgba16Float`。

1. 背景推定: 入力を σ = 背景除去 px / 3 でぼかす（分離可能、横 → 縦）
2. 星抽出: `star = max(入力 - 背景 - 明るさ下限, 0)`
3. グロー生成: 4 成分ガウシアン PSF
   - σ 倍率: 0.25 / 0.60 / 1.00 / 2.20（芯 → 裾）
   - 重み: 0.55 / 0.25 / 0.13 / 0.07（合計 1.0）
   - 明るさしきい値係数: 0.00 / 0.05 / 0.15 / 0.35（芯 → 裾）
   - 基準 σ = 半径 px / 3。各成分はエネルギー保存。
   - 各成分は畳み込み前に「明るさ応答 x しきい値係数」を星成分から引く（4.7 節）。
4. 合成: `ゲイン = 強度 x 不透明度` を掛けて Screen または Add
   - Screen も Add も「不透明度で線形補間」と「グローに不透明度を掛ける」が一致するため、
     シェーダではゲインへ畳み込んでいる（`BlendMath` のテストで等価性を検証）。

各レイヤーは常に**元画像から**星を抽出し、合成先だけが積み上がる。

タイル設計:

- マージン = 背景ぼかし半径 + 最大グロー半径（両者は直列に掛かるので足す）
- タイル寸法 = マージン x 4 を 256 画素単位へ丸め、2048〜3072 に収める
- 1 つのコマンドバッファへ 4 タイルまで詰める（同期回数を減らすため）。
  キャンセルの粒度はこのバッチ単位になる
- 実効半径は 3σ（それより外の寄与は 0.3% 未満）

読み書きを分けた ping-pong 構成にしてある。
これは当初 read-write tier 1 の GPU でも動かすための配慮だったが、
対象を Apple Silicon に絞ったため制約としては不要になった（構成はそのまま維持している）。

### 4.6 実測値

Apple M4 Pro / 8640 x 4860 / 1 レイヤー:

| 条件 | タイル数 | 所要時間 |
| --- | --- | --- |
| 標準グロー（半径 20px） | 15 | 約 0.16 秒 |
| 広いハロー（半径 60px） | — | 約 0.5 秒 |

当初はタイル寸法 1024（45 タイル）で約 0.2 秒だった。
タイルを大きくするとマージンの無駄（23% → 11%）と CPU-GPU 同期回数（45 → 4）が減る。

### 4.7 明るさに対する応答

畳み込みは線形なので、しきい値が無いと星の明るさが変わっても PSF の**形**は変わらず、
振幅が比例するだけになる。ガウシアンの裾は `exp(-r²/2σ²)` なので、
視認できる半径は `r ∝ √(ln B)` でしか増えない。
**明るさが 10 倍でもハロー半径は 1.5 倍程度**にしかならず、
明るい星と暗い星でハローの大きさに差が出ない。

実写では明るい星ほど目に見えて大きなハローを持つため、
成分ごとに明るさしきい値を設けて **PSF の形自体を明るさで変える**方式を採った。

- 成分 i の入力は `max(star - 明るさ応答 x しきい値係数_i, 0)`。
- 広い成分ほど係数が大きいので、暗い星は芯だけ、明るい星は裾まで乗る。
- 「明るさ応答」（0〜1、既定 0.5）で全成分のしきい値を一括調整する。
- 0 のときは全成分のしきい値が 0 になり、従来どおりの線形挙動に戻る。

しきい値は畳み込みの**横パスの読み込み時**に引く（`blurHorizontal`）。
追加のパスが要らないので、成分数を増やしても処理時間は変わらない。

### 4.8 グローのみ表示

追加されるグロー成分だけを確認するための表示モード（`GlowOutputMode.glowOnly`）。

- 原画を含めず、すべてのレイヤーを加算合成する。
- Screen 指定のレイヤーもこのモードでは加算になる（成分そのものを見るのが目的のため）。
- レイヤー別グローを保持しているので、切り替えても再処理は要らない（4.9 節）。

### 4.9 レイヤー別グローの保持

グローは「畳み込み → ゲイン → 合成」の順に処理される。
**後段はすべて線形**なので、畳み込み結果さえ保持しておけば描画時に適用できる。

- 各レイヤーのグローを **ゲイン適用前**の `rgba16Float` フル解像度テクスチャで保持する
- 表示はキャンバスのフラグメントシェーダが毎フレーム合成する
- 書き出しは `compositeLayers` カーネルが同じ式で合成する（見え方が一致する）

再処理が要るのは `GlowConvolutionKey` の値が変わったときだけ。

| 変更 | 扱い |
| --- | --- |
| 半径、背景除去、明るさ下限、明るさ応答 | 畳み込みからやり直す |
| 強度、不透明度、合成モード | 描画時に適用（再処理なし） |
| 表示/非表示、並べ替え、グローのみ表示 | 描画時に適用（再処理なし） |
| レイヤー追加 | 追加分だけ処理する（既存は再利用） |

非表示のレイヤーも畳み込んでおく。表示切替を再処理なしで即座に反映するため。
同時に扱えるレイヤーは 8 枚（シェーダのテクスチャ配列サイズ）。

VRAM の内訳（8640 x 4860 = 42M 画素、16bit x 4 チャンネルで 1 枚 336MB）:

| 用途 | フォーマット | サイズ |
| --- | --- | --- |
| 原画 | rgba16Unorm | 336 MB |
| レイヤー別グロー | rgba16Float | 336 MB / レイヤー |
| タイル中間バッファ 4 枚 | rgba16Float・2160² | 149 MB（処理中のみ） |
| 書き出し時の合成先 | rgba16Unorm | 336 MB（書き出し時のみ） |
| ドロウアブル | bgra8Unorm・画面サイズ | 約 44 MB |

**表示そのものは画面解像度の 8bit なので軽い。** 容量を使うのは画像データ本体である。

### 4.11 明るさ下限と星の分布

`明るさ下限`（旧「明るさ下限」）は、背景減算後の星成分から一律に引く下限値。

- 小さい値（0.001〜0.01）は高 ISO ノイズの抑制に効く
- 大きい値（0.1〜1.0）は暗い星を切り捨て、明るい星だけにグローをかける

指定テストデータでの実測（背景減算後の星成分、間引きサンプル 1050 万画素）:

| 分位 | 明るさ |
| --- | --- |
| 中央値 | 0.0001 |
| 上位 1% | 0.033 |
| 上位 0.1% | 0.232 |
| 上位 0.01% | 0.720 |
| 最大 | 0.875 |

| しきい値 | 残る画素 |
| --- | --- |
| 0.004（既定） | 11.6% |
| 0.01 | 2.7% |
| 0.05 | 0.73% |
| 0.1 | 0.37% |
| 0.2 | 0.13% |
| 0.4 | 0.03% |

「明るい星だけ」に絞るには 0.2 以上が要るため、範囲は 0〜1.0 とした。
既定値 0.004 は線形スライダーでは左端に潰れるので、UI は対数目盛りにしている。

分布は `GlowPipeline.measureStarHistogram` が GPU で集計する（背景減算までで止める）。
明るさ下限を動かしても測り直す必要はなく、背景除去が変わったときだけ再計算する。
インスペクタにはこの分布と、しきい値の位置・グロー対象の割合を表示する。

## 4.10 キャンバス描画の座標系

拡大縮小とパンは **テクスチャ座標で表現する**。ビューポートは描画領域全体に固定する。

当初はビューポートを画像の描画矩形に合わせていたが、
8640px の画像を等倍表示すると Retina で 17280px となり、
Metal のビューポート上限（16384）を超えて描画が破綻していた。
パンで原点が動くと歪み方が変わるため「2 本指ドラッグでアスペクト比が変わる」症状になる。

- `CanvasViewState.textureMapping` が画面座標（左上原点 0〜1）から
  テクスチャ座標への変換係数を返す
- シェーダは `uv = screenCoord * scale + offset` で変換し、範囲外は背景色で塗る
- スプリット比較の境界も画面座標で判定するため、拡大してもマウス位置と一致する

アスペクト比が倍率によらず保たれることは `CanvasViewStateTests` で検証している。

- シェーダへ渡すパラメータ構造体のメモリレイアウト
- Metal 実機でのグロー処理（一様画像は不変、点像がにじむ、進捗通知、キャンセル）
- タイル分割の結果が単一タイル処理と一致すること（マージン設計の検証）
- 指定テストデータのフル解像度処理（Screen 合成で暗くならない、背景が一様に持ち上がらない）
- 処理結果 → CGImage → 最終 TIFF の往復で画素が変化しないこと
- 未適用の変更がある間は書き出しを行わないこと
- 明るさしきい値の並び（芯は 0、裾ほど高い）と明るさ応答によるスケール
- 明るさ応答を上げたとき、暗い星の方が明るい星より強く削られること
- グローのみ表示に原画が含まれないこと、レイヤーが無ければ黒になること
- 中止で自動処理が止まり、手動の適用で再開すること
- 畳み込みに影響しない変更（強度、不透明度、合成モード、表示切替）で再処理を要求しないこと
- 保持したグローを使い回し、ゲインだけ変えて合成し直せること
- 非表示レイヤーが合成に含まれないこと、レイヤー数の上限を超えたら弾くこと

### 5.3 今後実装するテスト

- 単体テスト
  - パラメータ境界値（0%、最大半径、閾値上下限）
  - `.stellaveil` のエンコード/デコード
  - マスク生成・ブラシ編集のロジック
- 結合テスト
  - TIFF 読み込み → プレビュー → 書き出しの一連処理
- 回帰テスト
  - 既知プロジェクトの再読込一致
  - 同一入力での出力差分監視（許容誤差つき）

### 5.4 手動確認

- 強い前景光がある写真でのマスク漏れ確認
- 等倍表示で星のにじみ形状を確認
- プレビューと最終書き出しの見た目一致を確認
- メタデータ検証済み表示とタグ数表示を確認
- 各フェーズ完了時にアプリを起動し、スクリーンショットで確認してからコミットする

## 6. リスクと対策

| リスク | 対策 |
| --- | --- |
| メタデータ差分判定の過検知 | 除外タグを明示リスト化し、比較正規化を固定（§3.2 / §3.3） |
| 高解像度処理での待ち時間増大 | タイル分割による段階表示とキャンセルで待ちを隠す。縮小プレビューは見た目が変わるため採用しない（§4.1 / §4.3） |
| 自動マスクの誤検出 | 手動補正を前提機能として同一フェーズで実装する（フェーズ5） |
| Metal の read-write tier 1 GPU で動かない | ping-pong 構成で `read_write` テクスチャを使わない（§4.5） |
